# Private-connectivity production release support

Status: ratified
Ratified: 2026-11-15 by Brett Heap, through [register-private-connectivity-release-members](../../proposal.md).

## Purpose

Ensure that the supported neutral connectivity package is completely described by its release inventory while historical release and source-evidence identities remain independently verifiable.

## ADDED Requirements

### Requirement: Canonical connectivity publication has closed release membership

At and after the authorized first publication floor, a connectivity publication SHALL register and inventory its supported schema, contract README, conformance corpus and validator with their canonical identities, exact regular-file paths, declared schema version and raw Git-blob digests. Missing, extra, duplicate or mismatched registrations, missing members, symlinks, traversal and a declared-but-unreadable family MUST fail. An inventory builder success that omits these members MUST NOT qualify publication.

#### Scenario: Complete first supported publication
- **WHEN** the authorized cut contains the four canonical artifacts and exact registrations
- **THEN** its generated bytewise-sorted inventory includes all four raw-byte identities and the schema identity/version

#### Scenario: Manifest registration alone is insufficient
- **WHEN** the files are registered but one required artifact is absent or omitted from the inventory
- **THEN** build or verification fails rather than reporting a complete supported publication

#### Scenario: Registration and source boundaries are closed
- **WHEN** a publication substitutes an ID/type/path/version, duplicates a row or supplies an unsafe member
- **THEN** the existing closed membership and safe-input gates refuse it

### Requirement: Publication preserves historical release meaning

The first publication's release-semantic floor SHALL be fixed only at its authorized actual cut. Earlier bundles MUST retain their original membership and verification, even in a fixture where later family paths are present. The next release inventory MUST be builder-generated; prior inventories and immutable tags MUST NOT be rewritten.

#### Scenario: Earlier bundle with later files present
- **WHEN** verification evaluates a bundle below the first connectivity floor with later connectivity paths in the source fixture
- **THEN** those paths do not retroactively join that historical release

#### Scenario: Published baseline readback remains valid
- **WHEN** the current builder verifies the earlier published baseline at its own immutable tag
- **THEN** it reproduces that baseline's recorded membership and raw-byte digests

#### Scenario: Cut metadata is not allocated by drafting
- **WHEN** this change is proposed or ratified for source scope
- **THEN** no bundle version, generated inventory filename or tag is reserved or published by that act

### Requirement: Authorized refinement preserves accepted source evidence

The owner-approved T018 file refinement SHALL preserve all task identities, owners, classes, dependencies, cases, commands and frozen input bodies except its two explicitly accepted file additions and the resulting complete definition identity. Accepted historical evidence MUST retain its actual control, matching frozen reader and original immutable graph. A bridge SHALL accept only the specifically reviewed control/definition/reader identities and apply current authority revocations and closures throughout recursive and cached verification.

#### Scenario: Pending T020 packet precedes the refinement
- **WHEN** the current T020 actual-output packet remains unauthenticated
- **THEN** its definition and binding remain unchanged and the definition-changing implementation waits for its actual authentication and full default verification

#### Scenario: Fixed accepted history survives a later definition
- **WHEN** the refined reader consumes an exactly registered accepted prior source packet
- **THEN** it verifies that packet through its fixed original reader/definition and applies current authority state to every dependency

#### Scenario: Caller-selected or unaccepted history is refused
- **WHEN** a caller substitutes a control, core, reader bytes or definition, or supplies an unaccepted pending packet
- **THEN** the bridge refuses admission without executing caller-selected code

### Requirement: Source scope and publication authority remain separate

Ratification SHALL authorize only the exact accepted source/refinement scope. New source and collected CI outputs require their own actual authentication and full default verification. A real release cut, reviewed landing, promotion, annotated-tag publication and independent content readback MUST follow current release authority and policy. None of those acts SHALL provide full Q0 or Q1–Q5 acceptance.

#### Scenario: Source qualification is not publication
- **WHEN** the bounded reader/builder changes pass local and CI checks
- **THEN** the result proves their source behavior and supplies no missing cut/tag or rollout authority

#### Scenario: Actual supported release is independently consumed
- **WHEN** T018 has completed its authorized cut, reviewed publication and actual evidence admission
- **THEN** T019 independently verifies the real tag, release commit, inventory and consumed content before consumer pins advance

#### Scenario: A later candidate or new output is not pre-authenticated
- **WHEN** scope acceptance exists but the proposed source/CI output or publication candidate changes
- **THEN** any required actual output review and release authorization are obtained for that concrete result
