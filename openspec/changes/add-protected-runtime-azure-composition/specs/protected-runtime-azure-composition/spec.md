## Purpose

Define the proposed source-level Azure composition and evidence boundaries that allow a later separately authorized machine pilot to reuse accepted local primitives without inventing remote trust, generation-safe deletion or operational authority.

## ADDED Requirements

### Requirement: Design acceptance supplies no implementation or operation

The composition SHALL distinguish accepted T013-S1 design inputs from unratified P3 source semantics, unconfirmed appointments and every operational stage. Source implementation MUST require exact-candidate acceptance and explicit isolated commissioning; setup, dispatch, actual-run authority and cleanup MUST remain separate.

#### Scenario: Planning is complete
- **WHEN** this proposal and its feature plan validate
- **THEN** implementation and operational grants remain absent and no owner-act checkbox is inferred

#### Scenario: Roles are only nominated
- **WHEN** a proposed human or service identity has not been confirmed
- **THEN** deployment acceptance remains incomplete without impersonation or fabricated access evidence

### Requirement: Existing runtime contracts and refusal remain compatible

The composition SHALL preserve neutral APIs, three manual inputs, seven runtime roles, eight source roles, accepted static/full/report profiles and the unconditional original default refusal. A separate source-selected route MUST require review and exact source acceptance; configuration, environment flags, plugins and fixture credentials MUST NOT activate it.

#### Scenario: Default route is invoked
- **WHEN** no separately selected accepted route exists
- **THEN** it refuses before outputs or OIDC acquisition

#### Scenario: A caller edits configuration
- **WHEN** a file, flag, profile or input requests the deployment builder
- **THEN** the request cannot select or activate that capability

### Requirement: Remote facts preserve actual local provenance and complete bytes

The composition SHALL measure process/kernel/files beside the actual workload through protected local helpers and authenticate exact case/source/plan/run/attempt/incarnation/process evidence remotely. Independent final authority MUST validate complete canonical configuration and policy bytes and closed late derivation against independently selected observer facts; remote JSON or a digest alone MUST NOT masquerade as local measurement.

#### Scenario: Accepted local and remote observations agree
- **WHEN** real protected local observations and independently derived complete bytes match current approved scope
- **THEN** the proposed composition can proceed to unchanged full admission

#### Scenario: Remote process or bytes are substituted
- **WHEN** a remote PID, boot identity, caller JSON, observer identity or canonical byte differs
- **THEN** finalization refuses without fabricating local kernel evidence

### Requirement: Runner token transport has explicit trust and secret boundaries

The selected route SHALL freeze original trusted runner-injected endpoint/bearer before untrusted execution, enforce exact approved HTTPS origin/path/query policy and reject redirects, proxies and later mutation. It MUST treat injection as an explicit platform trust input, verify the resulting token and independent provider correlation before readiness, and prohibit discovery tokens or worker access to request credentials.

#### Scenario: Bounded phase request is authorized
- **WHEN** frozen runner transport matches trusted selected policy and one phase acquisition is separately authorized
- **THEN** only that audience-bound request can proceed and full signed-claim/provider checks remain mandatory

#### Scenario: Endpoint confusion or credential export is attempted
- **WHEN** an origin, duplicate query, preset audience, redirect, proxy, post-capture value or worker-visible bearer is supplied
- **THEN** the source path refuses before sending credentials

### Requirement: Images and disks match the accepted readers

The deployment SHALL use a measured managed-image artifact built from the accepted exact base and independently bind its provider ID/build/source measurement. It SHALL remain within existing OS-plus-one-data-disk per-host bounds, with at most one retained control disk and one retained gate disk in this composition; retained state MUST survive disposable VM retirement.

#### Scenario: Exact build and compatible disks are observed
- **WHEN** actual provider image ID/build and the selected two trusted-host retained disks match
- **THEN** the unchanged reader can validate them without a marketplace-ID substitution

#### Scenario: Image or layout is incompatible
- **WHEN** only a mutable marketplace reference, unexpected disk or unmeasured build is supplied
- **THEN** deployment admission refuses without widening existing readers

### Requirement: Issuance and local helpers exclude the workload

Every trusted service/helper SHALL authenticate independently selected role/incarnation/source/fingerprint/nonce and effective returned scope/expiry, using approved bootstrap authority. The workload MUST have no privileged assigned identity, App/custody key, helper credential, issuer/admin capability or ability to change measurement/state policy. Host-root and platform administrators MUST remain an explicit TCB.

#### Scenario: Allowed service and denied worker use valid requests
- **WHEN** the approved service succeeds and the worker submits the corresponding known-good canonical request
- **THEN** worker authority is explicitly denied while service availability is established

#### Scenario: A role self-approves enrollment
- **WHEN** a CSR, candidate, bootstrap-key holder or requested scope claims its own approval
- **THEN** issuance refuses without independent provider/authority corroboration

### Requirement: Infrastructure ownership is separate from runtime cleanup

The composition SHALL use factory-owned closed reservation/provisioned envelopes, a later final-scope link and a retirement receipt. Pre-create reservation MUST forbid unavailable provider/static/full/run facts; provisioned facts MUST preserve the complete reserved set/attempt/owner and precede independent static selection; the final link MUST bind actual approved sources/configuration/case/run/lease without a backward commitment cycle. It MUST NOT encode cloud VMs/disks as existing process/file kinds or add hidden fields to old reports. Overall deployment acceptance SHALL require both current runtime cleanup and independent infrastructure outcome.

#### Scenario: Both cleanup scopes pass
- **WHEN** runtime cleanup and separately authenticated exact infrastructure retirement/preservation are complete
- **THEN** the owner can assess both artifacts without changing old profile semantics

#### Scenario: Only one scope completes
- **WHEN** process cleanup succeeds while cloud retirement fails or the reverse
- **THEN** overall deployed qualification remains incomplete

### Requirement: Resource paths cannot acquire replacement generations

The controller SHALL durably reserve each selected ARM path and consume one create attempt before send, retain permanent tombstones and exclude every ordinary writer except the selected provisioner. It MUST require authenticated terminal creation plus per-kind incarnation and prohibit name reuse even after cleanup/evidence expiry. Ambiguous sends or pending updates MUST quarantine scope without retry/reset.

#### Scenario: Concurrent creates target one name
- **WHEN** two contenders request an unused approved path
- **THEN** only one durable creation attempt exists before any provider send

#### Scenario: A consumed or retired name is reused
- **WHEN** a restart, closed case, missing state or expired evidence attempts to reallocate the path
- **THEN** allocation refuses and the tombstone remains

### Requirement: Retirement uses proven controller fencing and per-kind identity

Retirement SHALL first close write/run authority, bind retiring state and fresh accepted per-kind incarnation, and prove no ordinary replacement writer or outstanding create/update. It MUST NOT claim Azure generation-precondition deletion where undocumented or substitute tags-then-delete, broad RG deletion, force deletion or a foreign/shared/retained target. Unsupported per-kind semantics MUST block eligibility.

#### Scenario: Selected generation is retired
- **WHEN** the permanent namespace and effective writer exclusions hold with matching fresh identity and terminal prior operations
- **THEN** only the enumerated ephemeral generation may enter bounded retirement

#### Scenario: Replacement or identity uncertainty appears
- **WHEN** a simulated bypass writer, foreign incarnation, missing fence or unsupported type is observed
- **THEN** retirement refuses and live acceptance remains blocked

### Requirement: External watchdog reconciles actual outcomes

The independently administered watchdog SHALL survive loss of the three hosts, retain authoritative reconciliation scope, deduplicate triggers and reconcile only original operations under bounded expiry. Pre-run setup failure/expiry/abort SHALL use original reservation/setup-cleanup authority without requiring nonexistent final-run facts; post-run evidence SHALL bind the actual final scope. Separately current read-only observation authority MAY report late failure after mutation expiry without renewing mutation/proof authority or budgets; missing observation authority MUST refuse emission and fail qualification. Accepted sends/HTTP202/timer schedules MUST NOT imply completed cleanup; authenticated terminal outcome and independent absence/revocation/retained/shared preservation readback are mandatory.

#### Scenario: Control host dies
- **WHEN** the original registered scope remains accessible to the separate watchdog
- **THEN** only its accepted generation is reconciled and independent results determine completion

#### Scenario: Delete outcome is ambiguous or delayed
- **WHEN** a response is lost, operation is pending, timer fails or independent readback is unavailable
- **THEN** the result remains pending/indeterminate/incomplete without a fresh grant or automatic send replay

### Requirement: Current budgets and redaction remain mandatory

All composition and nested provider/remote reads SHALL share existing phase budgets and earliest wall/monotonic deadlines, including existing response/body caps. A complete positive that cannot fit MUST fail source acceptance until separately governed change. Evidence MUST omit raw tokens, bearer URLs, credentials, private keys, provider payloads and human-factor/browser material.

#### Scenario: A nested call exhausts the original budget
- **WHEN** a remote/provider read consumes the last allowed slot or deadline
- **THEN** no fresh budget or late upgrade permits continued authority

#### Scenario: Fixture or private material is relabeled
- **WHEN** a caller offers copied pass flags, synthetic origin or sensitive payloads as protected evidence
- **THEN** reporting refuses and source-only scope remains honest

### Requirement: Source qualification and consumer acceptance stay separate

Future source acceptance SHALL require substantive real-local crypto/process/TLS/state tests with independent positive and single-mutation controls, preserved mandatory matrix identities and owned-fixture cleanup. It MUST NOT establish actual Azure allocation, protected claims, effective administration, human assurance or consumer058 T002 acceptance.

#### Scenario: Isolated tests pass
- **WHEN** the proposed adapters pass source conformance and cleanup
- **THEN** T013 operational selections and T014/T015 live/consumer/human gates remain separate

#### Scenario: A live prerequisite is missing
- **WHEN** actual deployment, independent protection/claims or cleanup evidence is absent
- **THEN** qualification stays blocked or not-performed without a synthetic substitute
