## Decisions

### D1 — Explicit protected-staging allocation

Only the trusted protected controller selects this allocation on a fresh Decision,
after signed purpose/phase/static plan authentication and before any observed
read. No worker field, body/CLI flag, late upgrade or joined decision selects it.
At most two complete observations are allowed, each retaining the accepted
four-request correlation reader, three protection reads (environment plus at most
two policy pages), four source reads and two control reads. Shared totals are
8/6/8/4 and twenty-six aggregate GitHub reads. Private operations are at most
sixteen; the complete current controller path consumes fifteen. ARM/key limits
stay 24/3. Ordinary allocation remains protection/source/control/correlation
3/4/2/4 (thirteen total), private twelve; accepted finalization remains six
protection observations/eighteen protection/twenty-eight total and private twelve.

Count each complete staging observation before its first I/O; a third refuses
even if earlier reads used less than their maxima. Each reader instance refuses
a fifth correlation request before credential access or I/O. All member/aggregate
high-water and group counts persist across client reconstruction. A staging
ledger cannot join an independent authority or upgrade to finalization.

### D2 — Repeat complete authority before opening the start request

The first complete correlation precedes every reservation/host registration.
Register and independently acknowledge the exact durable unit/cleanup lease.
Before invoking the private start client, repeat all signed identity, actual run/
job/eligible-human review, source/workflow/control/hold, current operator context
and environment protection checks using the same ledger and original Decision.
Compare the same selected plan/scope. Only then consume/send one start request.
Do not place this full refresh in the after-TLS callback: the private request
body is already serialized there and its idle peer is bounded. Performing it
before opening the request propagates the tightened absolute deadline in its
body/remaining transport timer. The after-TLS grant/lease check remains, as do
the host's pre-execution grant/lease/source checks.

No fresh clocks, retries, snapshot reuse, dropped checks or counter resets are
allowed. A failed refresh preserves registered cleanup ownership and never
starts a worker. Status-only recovery uses one complete current observation and
cannot call registration/start again. Provider reads do not establish atomic
future administrator behavior; the existing coordinated-hold TCB stays explicit.

### D3 — Qualification and source ownership

Feature017 adds late hold/main/control/context/protection/run/review mutations,
original clock/earliest-expiry checks, complete positives, observation/read caps,
unchanged ordinary/finalization allocation and no budget reconstruction/join.
Actual TLS and current independent sources remain mandatory. Host readback must
receive an earlier expiry discovered only by the second observation; no worker
instructions can cross after it expires. Qualification does not promise that all
remote reads finish in ten seconds: delay refuses rather than expanding time.

The factory owns this proposed allocation; adapter feature017 owns source and its
sole executable list. The accepted source packets remain byte-identical. Source
ratification and landing of the reviewed pair are separate later owner actions.

## Risks / Trade-offs

More reads within the same ten-second envelope can increase refusal under actual
provider latency. Qualify that operationally later; no cache, retry or longer time
is inferred. This corrects current checks at the source launch boundary, not an
atomic provider transaction or hostile-administrator guarantee.
